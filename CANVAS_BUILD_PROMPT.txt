--------------------------------------------------------------------------------
0. ONE-PARAGRAPH BRIEF
--------------------------------------------------------------------------------
Dashboards today are a JSON/pydantic spec (DashboardSpec) rendered onto a CSS
grid of typed widgets. Canvas is the opposite end of the flexibility spectrum:
the source of truth is an HTML document the human (or LLM) writes directly. Data
comes alive through Nubi custom elements (e.g. <nubi-kpi query-id="...">) and
{{token}} interpolation, exactly like the existing sanitized-HTML path — but
promoted from a single "html widget" to a first-class document type. Canvas
reuses the dashboards data layer (query/metric/connector resolution, RLS,
collect_board_data), the scheduled-send flow handler, the variable/cross-filter
runtime, and the LLM generate→validate→repair loop. It adds: a code+visual HTML
editor, a right-hand inspector that lets you select an element and bind it to a
query/metric/API connector, and persistence as a new resource type.

KEEP SCOPE TIGHT: reuse, don't reinvent. Every section below names the existing
file to copy/extend. Do NOT fork the dashboards data/RLS/scheduling code — share
it. Open-core rule still applies: anything billing/Paystack/cloud stays out of
OSS core (ee/ tree).

2. CORE MODEL — WHAT A CANVAS IS
================================================================================
A Canvas document is stored as a new resource type, parallel to "boards".
Recommended resource name: "canvases" (config column holds the doc).

CanvasDoc (config.doc) shape:
{
  "version": 1,
  "title": "Q3 Exec Brief",
  "html": "<section>...<nubi-kpi data-el-id='el_1' query-id='rev'>...</section>",
  "bindings": {                       // element-id -> data binding (see §3)
     "el_1": { "kind": "query", "query_id": "rev_total", "params": {...},
               "field": "total", "format": "currency" },
     "el_2": { "kind": "metric", "metric": { "metric_id": "...", ... } },
     "el_3": { "kind": "api", "connector_id": "...", "path": "/v1/x",
               "select": "$.data[0].value" }
  },
  "variables": [ { "name": "region", "type": "select", "default": "US" } ],
  "assets": { "css": "...optional scoped stylesheet..." },
  "theme": { ... optional ... },
  "schedule_hint": { ... optional, see §6 ... }
}

DESIGN DECISION (resolve early): bindings can live EITHER as element attributes
in the HTML (query-id="...", data-bind="el_1") OR in a side bindings{} map keyed
by a stable data-el-id. RECOMMENDATION: side map keyed by data-el-id.
- HTML stays readable and LLM-writable.
- The editor mutates bindings without rewriting the HTML string.
- Sanitization is simpler (fewer custom attributes to allowlist).
- {{token}} interpolation still works inline for text.
Custom elements (<nubi-*>) read their binding by data-el-id; plain elements can
also carry data-el-id to receive {{token}} text/attr injection.

3. DATA BINDING — THE "RHS SIDEBAR" CONTRACT
================================================================================
Binding kinds (mirror dashboards' three + promote API connector to first class):
  - "query"   -> query_id (+ params with {ref,pick} var substitution)
  - "metric"  -> MetricBinding (metric_id, dimensions, time_grain, filters)
  - "api"     -> connector_id (HTTP_JSON datastore) + path + JSONPath select
                 (reuse _resolve_connector's HTTP_JSON path in collect.py)
A binding targets a rendering surface:
  - a <nubi-kpi|table|chart|metric> custom element (full widget render), OR
  - a {{token}} in text / an attribute on a plain element (scalar/array inject).

Validation (server, extend validate_dashboard_html):
  1. HTML safety (existing checks).
  2. Every data-el-id referenced in bindings exists in the HTML, and vice-versa
     (orphan binding / unbound element = warning, not hard error).
  3. query_id / metric_id / connector_id exist in their registries (soft warn,
     like dashboards — agents may author before the query lands).
  4. At most one binding kind per element (hard error — mirror spec.py step 11).
  5. API connector must resolve to an HTTP_JSON datastore the org owns (hard).

5. THE RUNTIME (frontend) — RENDERING A CANVAS
================================================================================
- CanvasRenderer.jsx (new): wraps the rendered doc in the SAME context providers
  SpecRenderer uses — VariableProvider, CrossFilterProvider, RefreshProvider —
  so variables, cross-filter clicks, and auto-refresh "just work".
- Rendering pipeline:
     1. sanitizeDashboardHtml(doc.html)  (NEVER bypass this)
     2. set innerHTML on a container
     3. upgrade <nubi-*> custom elements (renderDashboardDoc.js); each element
        reads its binding by data-el-id, runs runArrowQueryById / runMetricQuery
        / the API connector fetch, and renders via the existing widget components
        (ChartWidget/KpiWidget/TableWidget) or chartOption.js.
     4. interpolate {{token}} text/attr bindings via renderWidgetHtml() with the
        resolved, HTML-escaped values.
- Public viewer /c/:id mirrors DashboardViewPage.jsx: GET /canvases/{id}, URL <->
  variable sync, read-only.

SECURITY (non-negotiable): all HTML — authored by humans OR LLMs — passes through
sanitizeDashboardHtml. Server independently re-validates on save with the
extended validate_dashboard_html. Data values are HTML-escaped before injection.
Honor existing RLS: data still flows through collect.py/run_query_rows, so per-
org RLS predicates and source_unsupported_rls guards apply unchanged.

7. LLM INTEGRATION — GENERATE / EDIT A CANVAS
================================================================================
Mirror backend/app/ai/dashboard.py with a canvas module
(backend/app/ai/canvas.py):
  - generate_canvas_doc(question, catalog, provider, model) -> CanvasDoc
       * System prompt teaches: write semantic HTML; use the nubi-* element
         vocabulary; attach data-el-id to anything data-bound; emit a bindings{}
         map; only safe tags (no script/style/iframe). Inject the element/binding
         JSON schema and the query/metric catalog + grounding, exactly like
         _SPEC_SYSTEM does for dashboards.
       * generate -> validate (extended validate_dashboard_html + binding checks)
         -> repair loop (MAX rounds, hard vs soft errors) -> loud 422 on failure.
  - edit_canvas_doc(doc, instruction, catalog, provider) -> CanvasDoc — diff-style
    edit ("make the header red", "bind this KPI to revenue"), same validate/repair
    loop. This is where Canvas shines for "quicker, more flexible LLM" — the model
    edits HTML directly instead of a constrained spec.
  - Routes (backend/app/routes/ai.py or a new canvas router):
       POST /ai/canvas        {question} -> {doc, html, grounding, valid, issues}
       POST /ai/canvas/edit   {doc, instruction} -> {doc, ...}
       GET  /ai/canvas/schema -> JSON schema of CanvasDoc + binding kinds
       POST /canvas/validate  -> stateless validation oracle (mirror dashboards)
  - Frontend "Ask AI" panel: lift ChatPanel.jsx / AskAIPanel.jsx; on accept,
    swap the editor's doc + bindings and mark dirty.
